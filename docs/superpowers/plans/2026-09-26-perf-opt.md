# gem5 perf-opt campaign, part 1 — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Speed up gem5's single-run simulation (KIPS) through build and host levers. Every lever must keep stats bit-identical to the baseline, and every trial is logged.

**Architecture:**
- A small harness in `util/perf-opt/` does the work:
  - pick and copy the checkpoints;
  - build a configuration;
  - run the 5-checkpoint suite, pinned to cores;
  - gate on stats identity;
  - tabulate KIPS.
- Each lever of the ladder is one trial: build → run → gate → table → log entry → commit → short report to the user.
- After the ladder: a hotspot profile, then a port to kratos2.

**Tech Stack:** bash, Python 3.12 (unittest), SCons 4.5, g++-12 12.4, `taskset`, perf 7.0, AMD uProf 5.3.

**Spec:** `docs/superpowers/specs/2026-09-26-perf-opt-design.md`

## Global Constraints

- **Toolchain:**
  - Every build goes through `util/perf-opt/build.sh`: g++-12, system Python, no conda, `--ignore-style`.
  - Builds before the tcmalloc trial pass `--without-tcmalloc`.
- **Runs:**
  - Every trial goes through `util/perf-opt/run_suite.sh`: `fs_run.py`, `--warmup-insts 10000000 --detailed-insts 30000000`, `--mem-size 16GiB`, cores 1–5, 1800 s timeout.
  - Builds never run while a trial runs.
- **Gate:**
  - `stats_gate.py gate` against `baseline-a`, with `docs/perf-opt/nondeterministic-stats.txt` excluded.
  - Accept iff all 5 checkpoints are identical **and** at least 3 of 5 are faster than the previous accepted configuration.
- **Logging:** every trial, including rejected ones, gets a subsection in `docs/perf-opt/performance-opt-log.md`. The format is fixed by spec §8.
- **Commits:** on `feat/opt` only.
  - A gem5 tag header of at most 65 characters, and a `docs/commit-notes/` note in the same commit.
  - The `.claude/skills/precommit-review` pass.
  - No AI trailers.
  - Never stage `CLAUDE.md` or the untracked bootloader binary.
- **Results:** never change simulated behaviour. Do not touch `have_large_asid_64`.
- **Cluster:** small probes only, following the cluster-etiquette rules.

## Review Focus

1. **A stale binary gets measured.** SCons can skip rebuilding when a flag is not sticky. Each trial has a "flag took effect" check on the built binary.
2. **A trial runs while the machine is busy** (a build or a copy). `run_suite.sh` records `loadavg_at_start`. A trial that started with a 1-minute load above 2 is re-run before any verdict.
3. **A new source of nondeterminism** (from a changed allocator or layout) looks like a behaviour change. On a gate failure, re-run the trial once:
   - the same diff again means a real change: reject;
   - a different diff means the run is nondeterministic: stop and ask the user.
4. **A resource lookup fails**: `fs_run.py`'s `obtain_resource` needs network access and an md5 check. `run_suite.sh` exits non-zero and names the checkpoint. Re-run; never accept a partial trial.
5. **Disk fills up** with many build dirs. Check `df -h /` before each build (at least 40 GB free). If needed, delete the object files of rejected configurations (keep their binaries).

### Trial procedure (Tasks 6–12 each run exactly this, with their own values)

For trial `<N>` with build dir `<DIR>`, variant `<VAR>`, compile flags `<CC>`, link flags `<LINK>`, scons args `<ARGS>`, run name `<TRIAL>`, and previous-run list `<PREV>`:

```bash
cd /home/rbera/work/agentic-cpu/gem5
RUNS=/home/rbera/work/agentic-cpu/perf-opt-runs
EX=docs/perf-opt/nondeterministic-stats.txt
df -h / | tail -1                                   # ≥ 40 GB free
CCFLAGS_EXTRA="<CC>" LINKFLAGS_EXTRA="<LINK>" util/perf-opt/build.sh <DIR> <VAR> <ARGS>   # nothing else running
<flag-took-effect check for this trial>
util/perf-opt/run_suite.sh build/<DIR>/gem5.<VAR> <TRIAL>
python3 util/perf-opt/stats_gate.py gate $RUNS/baseline-a $RUNS/<TRIAL> --exclude $EX
python3 util/perf-opt/kips_table.py --trial $RUNS/<TRIAL> <PREV> \
    --base $RUNS/baseline-a --base $RUNS/baseline-b --exclude $EX
```

Then:
1. **Log.** Append the trial subsection: heading; a one- or two-line summary; key idea; files and flags targeted with the exact build command copied from `build/<DIR>/perf-opt-build-<VAR>.txt`; the table printed by `kips_table.py`; build time and binary size; the verdict and its grounds.
2. **Commit** the log with header `misc: Log perf-opt trial <N> (<name>)`, a commit note, and the precommit-review pass.
3. **Report** to the user in a few lines: result, verdict, and what's next.

The accepted configuration after a trial (`ACC_DIR`, `ACC_VAR`, `ACC_CC`, `ACC_LINK`, `ACC_ARGS`, `ACC_RUN`) becomes the starting point of the next trial. `ACC_CC` and `ACC_LINK` are the accepted `CCFLAGS_EXTRA` and `LINKFLAGS_EXTRA` values. A rejected trial leaves them unchanged.

Initial values:
- `ACC_DIR=ARM ACC_VAR=opt ACC_CC='' ACC_LINK='' ACC_ARGS='--without-tcmalloc'`
- `ACC_RUN` is both baselines: `--prev $RUNS/baseline-a --prev $RUNS/baseline-b`.
